Type System
01

Type
Inference

Reading types from how arguments are used — not from what they are called.

Theory — how type inference works

The Method

Assign a fresh type variable to each unknown. Then read every operation as a constraint. Keep tightening until every variable is resolved — or until you realize something is polymorphic.

Polymorphism

When a function works for any type T — as long as the constraints are satisfied — the result is parametric polymorphism. The type signature contains T as a free variable, not a concrete type.

A function's type is a theorem about its behavior — derived from the constraints imposed by every operation inside it.

Scoping Rules
02

Lexical
vs Dynamic

The same function. Two languages. Two completely different answers.

Lexical

Free variables are bound at definition time. The function carries its environment as a closure. Source code structure determines everything.

Dynamic

Free variables are bound at call time. Walk the runtime call stack; use the first matching binding you find.

Closures capture references, not snapshots. A mutation after closure creation will be visible on all subsequent calls.

Language Extension
03

for / repeat
Rules

Reduce the guard. Base case. Unfold. The pattern never changes.

for E1 to E2 do C
Rule 1 — reduce E1
⟨E1,σ⟩ → ⟨E1',σ⟩
────────────────────────────────────
⟨for E1 to E2 do C,σ⟩ → ⟨for E1' to E2 do C,σ⟩
Rule 2 — reduce E2
⟨E2,σ⟩ → ⟨E2',σ⟩
────────────────────────────────────
⟨for n1 to E2 do C,σ⟩ → ⟨for n1 to E2' do C,σ⟩
Rule 3 — base (n1 > n2)
n1 > n2
────────────────────────────
⟨for n1 to n2 do C,σ⟩ → ⟨skip,σ⟩
Rule 4 — unfold (n1 ≤ n2)
n1 ≤ n2
──────────────────────────────────────────────────
⟨for n1 to n2 do C,σ⟩ → ⟨C ; for (n1+1) to n2 do C,σ⟩
repeat E times C
Rule 1 — reduce E
⟨E,σ⟩ → ⟨E',σ⟩
────────────────────────────────────
⟨repeat E times C,σ⟩ → ⟨repeat E' times C,σ⟩
Rule 2 — base (n ≤ 0)
n ≤ 0
────────────────────────────
⟨repeat n times C,σ⟩ → ⟨skip,σ⟩
Rule 3 — unfold (n > 0)
n > 0
──────────────────────────────────────────────
⟨repeat n times C,σ⟩ → ⟨C ; repeat (n−1) times C,σ⟩
key: E is evaluated once and decremented — not re-evaluated each iteration.

Why do most modern languages choose lexical scope over dynamic?
medium
1
Predictability
Under lexical scope, you can read the type and behavior of a function just by looking at its source. You don't need to know who called it.
2
Type checking
Static type checkers need to know what type a variable has at compile time. With dynamic scope, x could be Int or String depending on the call chain — unresolvable without running the program.
3
Closures
First-class functions (passing functions as values) only make sense with lexical scope. A function passed to a different call site would see completely different variables under dynamic scope.
Answer
Lexical scope enables static analysis, type checking, and safe first-class functions.
Parameter Passing
06

ref, name,
VR

Three modes. Three different moments of effect. Getting the order wrong costs points.

ModeKeywordMechanismWhen visible outside
Call by ReferencerefAlias to original variable. Reads and writes go directly to the caller's memory.Immediately, continuously.
Call by NamenameExpression is textually substituted. Re-evaluated at every use with the current state.At each use — may access different locations if other vars changed.
Call by Value-ResultVRValue copied in at call. Local copy used throughout. Final value copied back to caller on return.Only on return.
Call by Value(default)Value copied in. Function works on its own isolated copy.Never.
Call-by-name is the only mode where two consecutive reads of the same parameter may yield different values.
