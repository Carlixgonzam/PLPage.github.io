01

Type
Inference

Reading types from how values are used — not from what they are called.

mkStats · mkSummary · process

II — Scoping Rules
02

Lexical
vs Dynamic

Where a function is defined, or where it is called — the answer changes everything.

Lexical Scope

Resolve free variables in the environment where the function was defined. The closure carries its defining environment as a backpack.


Source code determines bindings. The call site is irrelevant.

Dynamic Scope

Resolve free variables by walking the call stack upward, finding the most recently bound value.


Runtime determines bindings. Where the function was written is irrelevant.

Closures capture references, not snapshots — a mutation after closure creation will be seen by subsequent calls.
Algorithm
How to solve scope problems
1. List all free variables (used but not a parameter or local)

2a. LEXICAL → go to the definition site in the source.
    Find the binding there. Check for mutations after closure creation.

2b. DYNAMIC → draw the call chain at runtime (stack).
    Walk top-to-bottom. Use the first binding found.

3. Substitute and evaluate.
Watch out: in the make / use example, y is assigned base=5, then f is created, then y is mutated to y*2=10. Under lexical scope f sees y=10 — because it closed over the reference, not the value at time of creation.
III — Language Extension
03

for / repeat
Rules

Extending SIMP with new loop constructs. The derivation pattern is always the same: reduce the guard, then base case, then unfold.

for E1 to E2 do C — Small-Step Rules
Rule 1 — Reduce E1
<E1, σ> → <E1', σ>
────────────────────────────────────────────
<for E1 to E2 do C, σ> → <for E1' to E2 do C, σ>
Rule 2 — Reduce E2 (E1 already value n1)
<E2, σ> → <E2', σ>
────────────────────────────────────────────
<for n1 to E2 do C, σ> → <for n1 to E2' do C, σ>
Rule 3 — Base case (n1 > n2)
n1 > n2
────────────────────────────────
<for n1 to n2 do C, σ> → <skip, σ>
Rule 4 — Unfold (n1 ≤ n2)
n1 ≤ n2
─────────────────────────────────────────────────────────────
<for n1 to n2 do C, σ> → <C ; for (n1+1) to n2 do C, σ>
repeat E times C — Small-Step Rules
Rule 1 — Reduce E
<E, σ> → <E', σ>
────────────────────────────────────────────
<repeat E times C, σ> → <repeat E' times C, σ>
Rule 2 — Base case (n ≤ 0)
n ≤ 0
─────────────────────────────
<repeat n times C, σ> → <skip, σ>
Rule 3 — Unfold (n > 0)
n > 0
─────────────────────────────────────────────────────
<repeat n times C, σ> → <C ; repeat (n−1) times C, σ>
Pattern: Always reduce E/E1/E2 to values before unfolding. The guard/count must be a concrete integer before the base or inductive rule can fire.

V — testScope
05

proc1

A classic nested procedure scope problem. The answer depends entirely on where you look for x.

procedure proc1() // x is FREE here

procedure proc2()

VI — Parameters
06

ref, name,
VR

Three modes, three different moments of effect. Getting these wrong is the most common source of mistakes.

Mode Keyword Mechanism External effect
Call by Reference ref Alias to the original. Reads and writes go directly to the caller's variable. Immediate and continuous.
Call by Name name Expression is textually substituted. Re-evaluated at every use with the current state. At each use — may access different memory locations.
Call by Value-Result VR Value copied in. Function uses a local copy. Final value copied back to caller on return. Only on return.
Call by Value (default) Value copied in. Function works on its own copy. Never.
Call-by-name is the only mode where the same parameter may yield a different value on two consecutive reads within the same function call.
The hidden trap: when ref changes a variable (like i) that is also part of a name expression (like a[i]), every subsequent use of that name parameter accesses a different location. Always trace ref effects first before evaluating name expressions on later lines.
