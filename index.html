Scoping Rules
02

Lexical
vs Dynamic

The same function. Two languages. Two completely different answers.

Lexical Scope

Free variables bind at definition time. The function carries its defining environment as a closure.

Dynamic Scope

Free variables bind at call time. Walk the runtime stack; use the first matching binding you find.

Closures capture references — not snapshots. A mutation after closure creation is visible on all subsequent calls.

03

for / repeat
Rules

Reduce the guard. Base case. Unfold. The pattern never changes.

for E1 to E2 do C
Rule 1 — reduce E1
⟨E1,σ⟩ → ⟨E1',σ⟩
──────────────────────────────────
⟨for E1 to E2 do C,σ⟩ → ⟨for E1' to E2 do C,σ⟩
Rule 2 — reduce E2
⟨E2,σ⟩ → ⟨E2',σ⟩
──────────────────────────────────
⟨for n1 to E2 do C,σ⟩ → ⟨for n1 to E2' do C,σ⟩
Rule 3 — base (n1 > n2)
n1 > n2
─────────────────────────────
⟨for n1 to n2 do C,σ⟩ → ⟨skip,σ⟩
Rule 4 — unfold (n1 ≤ n2)
n1 ≤ n2
──────────────────────────────────────────────────
⟨for n1 to n2 do C,σ⟩ → ⟨C;for(n1+1) to n2 do C,σ⟩
repeat E times C
Rule 1 — reduce E
⟨E,σ⟩ → ⟨E',σ⟩
──────────────────────────────────
⟨repeat E times C,σ⟩ → ⟨repeat E' times C,σ⟩
Rule 2 — base (n ≤ 0)
n ≤ 0
─────────────────────────────
⟨repeat n times C,σ⟩ → ⟨skip,σ⟩
Rule 3 — unfold (n > 0)
n > 0
───────────────────────────────────────────
⟨repeat n times C,σ⟩ → ⟨C;repeat(n−1) times C,σ⟩
Write the rules yourself
Operational Semantics — define rules for do C while B
Solution
-- do-while desugars to C ; while B do C
-- Only ONE rule is needed:

⟨do C while B, σ⟩ → ⟨C ; while B do C, σ⟩

-- The resulting while loop uses the existing while rules:
-- if B false → skip (stop)
-- if B true → C ; while B do C (continue)
do-while always runs the body at least once. After the first execution, it becomes a regular while loop.

proc1 looks at its defining environment → global level

ref, name,
VR

Three modes. Three different moments of effect. The order they fire matters enormously.

ModeKeywordMechanismVisible outside
Call by ReferencerefAlias. Reads and writes go directly to the caller's variable.Immediately.
Call by NamenameExpression re-evaluated at every use with current state.At each use — may access different memory.
Call by Value-ResultVRCopy in. Local copy throughout. Copy back on return.Only on return.

Call-by-name is the only mode where two consecutive reads of the same parameter can yield different values.
Predict the output
Parameter modes — trace test2(x, x) with same variable twice
Solution
At call time: a=ref to x (x=0), b_local=0 (VR copies x=0 once)

Line 1: a := a+10 → reads x=0, writes x=10 via ref
Line 2: b := b+5 → b_local=0+5=5 (local only, x unchanged)
Line 3: a := a+1 → reads x=10, writes x=11 via ref

Return: VR writes b_local=5 back to x → x = 5
(VR overwrites ref's x=11 — VR write-back happens last)

Final: x = 5 y = 0 (y was never passed or modified)
VR captures the value at call time (x=0), not the current value. On return, it overwrites whatever ref did to x.

Abstract Syntax Trees
09

AST
Structure

The tree is the program. Before semantics, before types — the shape of code.

The AST strips away syntax — parentheses, semicolons, whitespace — leaving only the structure that actually matters for evaluation.

What is an AST?

An Abstract Syntax Tree is the intermediate representation produced by the parser. Each internal node represents an operation; each leaf is a literal or variable. The tree encodes operator precedence and associativity structurally — no parentheses needed.

Grammar → AST

The grammar defines what strings are valid programs. The AST represents one parse — the specific tree chosen when there is ambiguity (via precedence rules). Evaluating a program means walking its AST.

SIMP grammar → AST node types
Grammar (simplified SIMP)
E ::= n | !l | E Op E
Op ::= + | - | * | /
B ::= true | false | E Bop E | ¬B | B ∧ B
C ::= l:=E | C;C | if B then C else C | while B do C | skip

Each production rule → one AST node type

Tree-walking evaluation
How to evaluate an AST
eval(Num n) = n
eval(Var x, σ) = σ(x) — look up in state
eval(BinOp(+,l,r),σ) = eval(l,σ) + eval(r,σ) — recurse on children
eval(BinOp(*,l,r),σ) = eval(l,σ) * eval(r,σ)

Evaluation is always bottom-up: leaves first, then internal nodes.

Operational Semantics
10

Big Step
vs Small Step

Two styles of operational semantics. Same program. Radically different granularity.

Big-Step (Natural Semantics)

Written ⟨C, σ⟩ ⇓ σ'. Means: starting in state σ, command C terminates and produces σ'. You build a derivation tree — the root is the whole program, the leaves are axioms. Works top-down.


Use when: you only care about the final result. Proofs are more compact.

Small-Step (Structural Semantics)

Written ⟨C, σ⟩ → ⟨C', σ'⟩. Means: one reduction step. You write a linear sequence of configurations, one rule per line. Ends at ⟨skip, σ_final⟩.


Use when: you need to reason about intermediate states, non-termination, or concurrency.

Big-step asks: what is the result? Small-step asks: what is the next step? Never mix the two in the same derivation.
Core rules — side by side
Big-step — assignment
⟨E, σ⟩ ⇓ v
─────────────────────────
⟨l:=E, σ⟩ ⇓ σ[l↦v]
Big-step — sequence
⟨C₁, σ⟩ ⇓ σ'    ⟨C₂, σ'⟩ ⇓ σ''
─────────────────────────────────

Program: x := 1 ; y := !x + 2   Initial state: σ = {x↦0, y↦0}

BIG-STEP DERIVATION TREE
Build tree top-down
    ⟨x:=1, σ⟩ ⇓ σ₁    ⟨y:=!x+2, σ₁⟩ ⇓ σ₂
   ─────────────────────────────────────────
   ⟨x:=1 ; y:=!x+2, σ⟩ ⇓ σ₂

where σ₁ = σ[x↦1]
and   σ₂ = σ₁[y↦3]

⟨x:=1;y:=!x+2, σ⟩ ⇓ {x↦1, y↦3}
Big-step shows the full justification as one tree. Each sub-derivation is a branch. The root is the whole program. You never see the intermediate states — only the final σ.
SMALL-STEP SEQUENCE
One rule per line
⟨x:=1 ; y:=!x+2, σ⟩
→ ⟨skip ; y:=!x+2, σ₁⟩  [assign x:=1]
→ ⟨y:=!x+2, σ₁⟩  [seq-skip]
→ ⟨y:=1+2, σ₁⟩  [deref !x=1]
→ ⟨y:=3, σ₁⟩  [arith 1+2=3]
→ ⟨skip, σ₂⟩  [assign y:=3]

Final: ⟨skip, {x↦1, y↦3}⟩
Small-step shows every intermediate configuration. You see exactly when each variable changes. The derivation is linear — one step at a time.
Common mistakes
Mistake 1 — mixing notation
Writing ⟨C, σ⟩ ⇓ ⟨C', σ'⟩

Wrong. ⇓ takes a command and produces a state, not a configuration.

Big-step: ⟨C, σ⟩ ⇓ σ'
Small-step: ⟨C, σ⟩ → ⟨C', σ'⟩
Mistake 2 — skipping steps
In small-step, writing
⟨!x+2, σ⟩ → ⟨3, σ⟩

Wrong if done in one step. Must show each sub-step: deref first, then arithmetic.

⟨!x+2, σ₁⟩ → ⟨1+2, σ₁⟩ → ⟨3, σ₁⟩
Mistake 3 — wrong while rule
In small-step, NOT:
⟨while B do C, σ⟩ → ⟨C;while B do C, σ⟩

Wrong — must check B first!

→ ⟨if B then (C;while B do C) else skip, σ⟩
Write it yourself
Choose a style and derive: x := 2 ; x := !x * !x
Solution — both styles
BIG-STEP:
  ⟨x:=2, σ⟩ ⇓ σ₁    ⟨x:=!x*!x, σ₁⟩ ⇓ σ₂
  ───────────────────────────────────────────
  ⟨x:=2 ; x:=!x*!x, σ⟩ ⇓ σ₂
where σ₁={x↦2}, σ₂={x↦4}

SMALL-STEP:
⟨x:=2 ; x:=!x*!x, σ⟩
→ ⟨skip ; x:=!x*!x, σ₁⟩   [assign, σ₁={x↦2}]
→ ⟨x:=!x*!x, σ₁⟩   [seq-skip]
→ ⟨x:=2*!x, σ₁⟩   [deref !x=2]
→ ⟨x:=2*2, σ₁⟩   [deref !x=2]
→ ⟨x:=4, σ₁⟩   [arith 2*2=4]
→ ⟨skip, σ₂⟩   [assign, σ₂={x↦4}]
Pick one style and be consistent. In small-step, show every deref and arithmetic step separately.

Can while true do skip be derived in big-step? What about small-step?
hard
1
Big-step
Big-step requires finding a final state σ'. A non-terminating program has no final state → no big-step derivation exists. Big-step cannot express divergence.
2
Small-step
Small-step just requires the next step. The while rule unfolds it to if-then, which fires C=skip, loops again — an infinite sequence of steps. Divergence is visible as a non-terminating sequence.
3
Conclusion
This is why small-step is preferred when reasoning about non-termination, concurrency, or reactive programs.
Answer
Big-step: no derivation (diverges).
Small-step: infinite sequence of steps.
